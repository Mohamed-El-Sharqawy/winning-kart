# Inbound webhook ingress: verify, enqueue, ack

Shopify (webhook-primary) and WooCommerce (webhook plus mandatory hourly poll) deliver to a public HTTPS endpoint on the self-hosted Winning Kart process, behind the operator's own TLS (Coolify/Traefik). Verified platform facts drive the shape: Shopify counts only 2xx within 5 seconds total (1s connect), retries 8 times over 4 hours, then deletes the subscription; WooCommerce never retries, auto-disables the webhook after 5 consecutive failures, and sends an unsigned activation ping (`webhook_id=<n>`) that must return exactly 200; neither platform signs a timestamp. So ingress never processes inline: every verified delivery becomes one row in the Postgres queue (ADR 0006) and is acked 200 within a second; an enqueue failure returns 503 so Shopify's retries (or Woo's reconciliation poll) heal it.

Routes are per-platform under `/api/webhooks`, registered by each adapter as a descriptor — segment, resolution strategy (`header-tenant` or `slug`), verifier — so new platforms add a descriptor, never new ingress code. Shopify resolves the connector from `X-Shopify-Shop-Domain` after verifying the base64 HMAC-SHA256 of the raw body with the app client secret held in operator env; Woo routes by an opaque per-connector slug URL verified with a per-connector secret Winning Kart generates and stores AES-256-GCM in `connectors.config` (the wizard forbids Woo's blank-secret fallback to the consumer secret). Unauthenticated posture: unknown target — route, slug, or shop domain — returns 404 with a byte-identical body; a known target with a bad or missing signature returns 401; never 403. The single carve-out: Woo's unsigned ping gets 200 with no processing. Dedup is authoritative at write time via the unique dedup-key index (`{shop_domain}:{order_id}` per spec 06); platform delivery ids (`X-Shopify-Webhook-Id`, `X-WC-Webhook-Delivery-ID`) are recorded for observability and `X-Shopify-Event-Id` for correlation. No timestamp gate exists where nothing is signed; any future platform that signs a timestamp gets a ±5-minute skew gate in its adapter. Webhook URLs are permanent for the connector's life — slug never rotates short of disconnect. Woo's mandatory hourly poll is a reconciliation job: the API process's cron enqueues it hourly with jitter, the worker pages `GET /wc/v3/orders` by `modified_after` watermark, "last successful poll" is the latest succeeded poll-stage row in `connector_sync_log`, and staleness beyond two intervals raises an Amber state plus a 09 alert.

## Considered Options

- **Inline processing** (as `/api/revenue/ingest` does today): rejected - Shopify's 5-second budget leaves no room, and a crash after ack loses work no platform will redeliver (Woo) or may delete the subscription trying (Shopify).
- **Generic endpoint with platform sniffing**: rejected - verification is inherently per-platform; the descriptor registry keeps ingress platform-agnostic without pretending otherwise.
- **403 for bad signatures**: rejected - semantically "authenticated but forbidden"; 401 for failed verification and 404 for unknown targets leaks no connector existence.
- **Dedup at enqueue**: rejected - races concurrent deliveries; the write-time unique index is the single authority, matching the existing ingest pattern (pre-check plus unique-violation catch).
- **Timestamp skew window for Shopify/Woo**: rejected - neither platform signs a timestamp; a gate over unsigned headers is security theater.

## Consequences

- Woo's 5-failure auto-disable and Shopify's 8-failure subscription deletion make endpoint uptime load-bearing for merchant webhook survival; reconciliation must also verify subscriptions exist and re-create deleted ones (owned by the platform adapter tickets, not ingress).
- The permanent-URL rule constrains all future route design: shape and slug values never change once issued.
